# hueforge-version

Version manifest server for HueForge. Hosted via GitHub Pages at `version.thehueforge.com`.

## Files

| File | Purpose |
|------|---------|
| `version.json` | App version, beta version, plugin versions |
| `external_links.json` | External link registry |
| `filament_libraries.json` | Vendor filament library manifest (auto-generated — do not edit by hand) |
| `filaments/*.json` | Vendor filament library files served to HueForge clients |
| `libraries.json` | Library hot-update manifest, `{schemaVersion: 1, libraries: [...]}` (auto-generated by `generate_library_manifest.py` — do not edit by hand) |
| `libraries/<platform>/<lib>-<version>.zip` | Library payload: the signed DLL + `library.json` (written by HueForge's `Tools/release/publish_library.py`) |
| `libraries/<platform>/<lib>-<version>.meta.json` | Payload metadata: `abiVersion`, `minHostVersion`, `maxHostVersion`, `notes`, `published` |
| `libraries/contracts/<hostVersion>/<lib>.imports.txt` / `.abi.txt` / `.deps.json` | What each HueForge release needs from each updatable library (imports of HueForge.exe + TD1Standalone.exe, ABI number, first-party header hashes), recorded by the installer build |

## Updating vendor filament libraries

1. Add or update `.json` files in `filaments/`
2. Commit — the pre-commit hook regenerates `filament_libraries.json` automatically

The manifest captures the SHA-256 of each file and the filament count. HueForge clients compare the SHA-256 against their local copy to detect updates.

## Recording a HueForge release's library contracts

`installer/build_installer.ps1` (HueForge repo) writes `libraries/contracts/<version>/` at every
release build when this repo sits beside the HueForge checkout (or `-VersionRepo <path>` names it).
Commit that folder with the release — a host version with no recorded contract can never be in a
payload's host range. By hand:

```bash
python Tools/release/record_library_contracts.py --data-dir <installer data dir> --build-dir build/Release --host-version <v> --source . --out ../hueforge-version/libraries/contracts/<v>
```

## Publishing a library update

Windows bench only (macOS and Linux stay full-release). From the HueForge repo, on the release
branch of the host line the payload targets (the header-hash check refuses any other tree):

1. Build and production-sign the library (e.g. `build/Release/libTD1.dll`), with its version
   bumped in the library's `hf_library_info`.
2. Run:
   ```bash
   python Tools/release/publish_library.py --dll build/Release/libTD1.dll --pdb build/libTD1/Release/libTD1.pdb --source . --version-repo ../hueforge-version --min-host 0.9.4.5 --max-host 0.9.4.99 --notes "What changed"
   ```
   It refuses on a bad signature or a thumbprint other than the production certificate, a DLL
   not on the host allowlist, no recorded host contract in the range, any symbol a host in range
   imports that the DLL does not export, an ABI mismatch, or a first-party dependency whose
   headers differ from a host's recorded hash. On success it writes the zip + `.meta.json`
   here, archives the PDB in `ReleaseSymbols/<lib>-<version>/`, regenerates `libraries.json`
   and prints `git status`.
3. Review, then commit and push this repo yourself (the script never does). A published
   `<lib>-<version>.zip` is immutable: fix forward with a new version.

## Setup (one time per clone)

```bash
git config core.hooksPath .githooks
```

This activates the pre-commit hook that auto-regenerates `filament_libraries.json` and `libraries.json`.

## Manual manifest regeneration

```bash
python generate_filament_manifest.py
# or with custom paths:
python generate_filament_manifest.py --dir filaments --base-url https://version.thehueforge.com/filaments --out filament_libraries.json

python generate_library_manifest.py
# or with a custom host:
python generate_library_manifest.py --base-url https://version.thehueforge.com/libraries --out libraries.json
```
